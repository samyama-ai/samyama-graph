# ADR-035: OEH — Order-Embedded Hierarchy Index (Subsumption + Index-Resident Roll-up)

## Status
**Partially shipped** (v0.9.x). Index, DDL, functions, two of the three planner
rewrites, snapshot round-trip and the HIER benchmark are in. The order-test rewrite is
specified below but **not implemented** — see Follow-ups.

## Date
2026-08-13

## Context

Three families of workload that Samyama already serves each carry a hierarchy, and each
is handled today by an unrelated mechanism:

| Domain | Hierarchy | How it is served today |
|---|---|---|
| Time | `day ⊑ month ⊑ quarter ⊑ year` | property predicates on a timestamp, or an application-side calendar table |
| Geography | `zip ⊑ city ⊑ state ⊑ country` | variable-length traversal `(x)-[:LOCATED_IN*]->(y)` |
| Ontology | `is-a` / `part-of` (MeSH, ATC, NCBI Taxonomy, ATT&CK, CWE) | variable-length traversal |

These are all the same mathematical object: a **subsumption poset** — a partial order
generated by a covering relation, stored in the graph as `child -[:IS_A]-> parent` edges.
Two operations dominate the workload:

1. **Order test** — is `x ⊑ y`? ("is this trial's condition under *cardiovascular disease*?")
2. **Hierarchical roll-up** — fold a measure over `{y} ∪ descendants(y)`.
   ("total enrollment across everything under *cardiovascular disease*")

Today both cost a variable-length expansion. The order test costs O(ancestors(x)) per row —
paid once per candidate row, so a filter that should be a predicate becomes a traversal.
The roll-up costs O(subtree) and cannot be shared across queries. On the ontology-scale KGs
(`pubmed-kg`, `clinicaltrials-kg`, `mitre-attack-kg`) subtrees run to 10^5–10^6 nodes, so a
single grouped roll-up query does tens of millions of edge traversals for an answer that is
a handful of numbers.

The prior art splits along a seam. Reachability indexes (2-hop/PLL, GRAIL, transitive
closure) answer the order test and nothing else. OLAP/time-series engines (TimescaleDB
continuous aggregates, SAP HANA hierarchy indexes) answer the roll-up, but either only for
one hard-coded hierarchy (time) or only *index-assisted* — the index supplies a subsumption
predicate and the engine still computes the aggregate with a join-group-aggregate over the
matched rows.

arXiv:2606.24677, *One Index for Subsumption and Roll-up across Time, Geography, and
Ontology* (Mandarapu & Kunkunuru), observes that one structure can answer both, and that the
right encoding is selectable from a cheap structural probe. The reference implementation
(`relationship-hierarchy-index`) validates this on Gene Ontology, NCBI Taxonomy (1.3M),
GeoNames (330k), a 2.6M-node calendar and git commit DAGs, exact against a brute-force
oracle, `git merge-base`, and TimescaleDB.

This ADR brings that capability into the engine as a first-class, planner-visible index.

## Decision

Add a **hierarchy index** kind — `OEH` — under `src/index/hierarchy/`, declarable from
Cypher, persisted in snapshots, and consulted by the planner without the user naming it.

### 1. The poset

A hierarchy index is declared over one or more **edge types** interpreted as the covering
relation, oriented `child -> parent` (`c -[:IS_A]-> p` means `c ⊑ p`). On build we:

- collect the induced subgraph over those edge types,
- deduplicate parallel edges,
- validate acyclicity by Kahn topological sort, caching the child-before-parent order,
- reject the build with a typed error on a cycle (a cyclic "hierarchy" is a data bug, and
  silently condensing SCCs would give wrong roll-ups).

Nodes with no parent are roots; the poset may be a forest.

### 2. Structural probe (the encoding knob)

A single pass over the parent lists classifies the poset and selects the encoding:

```text
every node has ≤ 1 parent            → NestedSet
otherwise, chain width ≤ width_cap   → Chain
otherwise                            → Declined
```

with `width_cap = max(64, 8·√n)`. The cap is principled, not tuned: chain-mode space is
O(n·width), so capping width at ~8√n keeps the index at ~O(n^1.5) — beyond that a 2-hop
index is the right substrate and OEH must get out of the way.

**Declining is a supported outcome, not a failure.** `CREATE HIERARCHY INDEX` on a
high-width DAG (Gene Ontology is the canonical case) returns a diagnostic naming the
measured width and the cap, no index is created, and the planner continues to use
variable-length expansion. We would rather report the regime boundary than build a
quadratic index and call it a win.

### 3. NestedSet encoding (trees)

Iterative DFS assigns each node an interval `[tin, tout]` over in-order ranks:

- **Subsumption** `x ⊑ y` ⟺ `tin[y] ≤ tin[x] ∧ tout[x] ≤ tout[y]` — two integer
  comparisons, O(1), no allocation.
- **Descendants of `y`** are the *contiguous* rank range `[tin[y], tout[y]]`, which is what
  makes the roll-up a range query rather than a set union.
- Space: 2 × u64 per node, plus one rank→NodeId inverse vector.

Iterative, not recursive: NCBI Taxonomy and calendar hierarchies are deep enough that a
recursive DFS is a stack-overflow risk on a 2MB thread.

### 4. Chain encoding (low-width DAGs)

Jagadish chain decomposition: partition the poset into disjoint chains in topological
(parent-before-child) order; each node gets `(chain_id, pos)`. For each node `v`, compute
`reach[v]: chain_id → min reachable pos`, folded children-before-parents.

- **Subsumption** `x ⊑ y` ⟺ `reach[y][chain_of(x)] ≤ pos_of(x)` — O(1) map probe.
- **Descendants of `y`** on chain `c` are the contiguous *suffix* from `reach[y][c]`.
  Because the chains partition the node set, summing per-chain suffix aggregates visits
  each descendant exactly once: the roll-up is **exact and double-count-free** even though
  a node may be reachable from `y` along many paths.

Double counting on multi-parent DAGs is the primary correctness hazard of this whole
design. It gets a dedicated test class (§7), not a passing assertion.

### 5. Monoid roll-up (index-resident)

Roll-up is parameterized over a commutative monoid `(identity, combine)`:

| Op | Invertible | Structure |
|---|---|---|
| `SUM`, `COUNT` | yes | **Fenwick tree** over in-ranks; range = prefix(hi+1) − prefix(lo). O(log n). |
| `MIN`, `MAX` | no | **Sparse table** over in-ranks; O(1) query, O(n log n) build/space. |
| generic | — | `RollupMonoid` trait seam; falls back to the sparse-table path. |

A Fenwick difference is only valid for an invertible monoid — MIN/MAX have no inverse, so
they get a structure that answers a range fold directly. The reference implementation scans
the subtree for MIN/MAX; we pay O(n log n) space once at build to keep the query O(1),
because the engine's roll-up is called in a loop by top-k queries (HIER class H8).

In chain mode both cases use per-chain suffix folds, which are correct for any commutative
monoid without an inverse.

The roll-up is **index-resident**: the answer is read out of the index structure. Nothing
downstream scans, joins, or groups the descendant rows. This is the property that separates
OEH from an index-assisted hierarchy index, and it is what turns O(subtree) into O(log n).

**Measure sourcing.** The measure is a numeric node property named at declaration time
(`MEASURE Trial.enrollment`). It is read through the columnar property store
(`node_columns`), *not* the sparse property map — after a snapshot import `node.properties`
is empty and the values live only in the columnar store (ADR-021). Reading the property map
would produce a silently-zero roll-up on every imported graph.

### 6. Lifecycle, staleness, persistence

OEH is a **static** index. Rather than pretend otherwise:

- Every index carries a `built_at_version` and a `stale` flag.
- Mutating an edge of a hierarchy's covering-relation type, or the declared measure
  property, marks the index stale. Node/edge changes elsewhere do not.
- A stale index is **not** used by the planner by default; the query falls back to
  variable-length expansion and `EXPLAIN` reports the fallback with its reason. A session
  may opt into stale reads explicitly for analytical workloads that tolerate it.
- `REBUILD HIERARCHY INDEX <name>` rebuilds from the current graph.
- **Declarations** serialize into `.sgsnap` (ADR-022) as an additive `"t":"h"` line type;
  the structures rebuild on import. Interval arrays and Fenwick trees expand to many times
  their in-memory size as JSON-lines, and a rebuild is one O(n + m) pass — a rounding error
  next to importing the nodes and edges they are built from. Because pre-ADR-035 readers
  dispatch on `"t":"n"` / `"t":"e"` and ignore other line types, the format version does
  not move and snapshots stay loadable on older builds.
- A hierarchy that declines on the imported data is registered with its diagnostic rather
  than dropped: the probe is a property of the data, and an import that reshapes the graph
  can move a poset into regime.

Online incremental maintenance is explicitly **out of scope for v1** (see Non-goals).

### 7. Correctness gates

Shipped as tests, not as a checklist:

- A brute-force `oracle` module (BFS ancestors/descendants, fold roll-up) ships in-tree.
- **All-pairs equality**: on every generated and fixture poset, `index.subsumes(x,y) ==
  oracle.subsumes(x,y)` for all n² pairs.
- **Roll-up equality**: `index.rollup(y, op) == oracle.rollup(y, op)` for every node, every
  monoid.
- **Double-count class**: diamond, multi-diamond, and randomly generated low-width DAGs
  where a naive path-sum over-counts; the test asserts the naive answer differs and the
  index matches the oracle.
- **Regime**: the width cap declines above the bound and builds below it.

### 8. Planner integration

Physical operators, visible in `EXPLAIN`:

- `HierarchyOrderTest` — O(1) subsumption predicate.
- `HierarchyRollup` — index-resident monoid fold.
- `HierarchyDescendantScan` — enumerate the descendant set from the index (the range in
  nested-set mode, the per-chain suffixes in chain mode) instead of expanding edges.

Rewrites, each behind a conservative detector in the style of
`adjacency_agg_detector.rs` (return `None` ⇒ standard plan, never an error):

1. `(x)-[:IS_A*]->(y)` / `*0..` / `EXISTS { … }` used as an existence test ⇒
   `HierarchyOrderTest`.
2. `MATCH (d)-[:IS_A*0..]->(root) RETURN sum(d.measure)` ⇒ `HierarchyRollup`.
3. `MATCH (d)-[:IS_A*0..]->(root) …` where `d` is otherwise consumed ⇒
   `HierarchyDescendantScan`.

Direct functions `subsumes(a, b)` and `hierarchy_rollup(root, 'measure', 'sum')` cover what
the rewrites cannot reach. Cost-model entries make the choice cost-based rather than a
hard override, and plan-shape regression tests assert the operator appears — an answer-only
test would pass on the slow path and hide a rewrite regression.

## Consequences

**Positive**
- One index kind serves time, geography and ontology; no per-silo machinery.
- Roll-up becomes O(log n) (nested-set) or O(width) (chain) instead of O(subtree).
- Cross-hierarchy conjunctions (ontology × time × geography in one query) become three
  O(1) predicates — the shape that motivated the paper and that no per-silo index answers.
- Subtree-restricted vector search becomes expressible: an O(1) predicate composes with
  HNSW filtering where a time-series engine has no analogue.

**Negative / accepted**
- Static index: writes to the covering relation invalidate it. Analytical hierarchies
  (calendar, ontology releases, geo) change rarely, which is why this is acceptable now
  and not forever.
- Chain mode costs O(n·width) space; the cap bounds it but a wide-ish DAG still costs more
  than nested-set's 2 ints/node.
- MIN/MAX cost O(n log n) index space for O(1) query — a deliberate space-for-time trade
  that SUM/COUNT do not pay.
- A third index kind to keep coherent with MVCC and snapshots.

## Alternatives Considered

- **2-hop labeling (PLL) for everything.** Answers subsumption well and is the right
  answer for high-width DAGs — which is why we defer to it above the cap. But it has no
  roll-up analogue: the descendant set is not contiguous under any PLL labeling, so the
  aggregate falls back to enumerate-and-fold. On trees it also costs ~2× the space and
  ~6–7× the build time of nested-set at query parity.
- **Transitive closure materialization.** O(n²) worst case; on a 1.3M-node taxonomy it is
  not a candidate.
- **GRAIL-style interval labels with exceptions.** Approximate filter plus verification —
  fine for reachability, but "verify by traversal" reintroduces exactly the cost the
  roll-up is trying to remove.
- **Push the calendar into a time-series engine and federate.** Solves time only, leaves
  ontology and geography unserved, and makes the cross-hierarchy conjunction a distributed
  join.
- **Materialized aggregate views per hierarchy.** Matches roll-up latency, but is
  per-hierarchy-per-measure, does not answer subsumption, and multiplies the staleness
  problem instead of localizing it.

## What shipped, and what did not

| Piece | State |
|---|---|
| Poset, acyclicity, structural probe, width cap | shipped |
| Nested-set and chain encodings, decline path | shipped |
| Monoid roll-up (Fenwick / sparse table / chain suffix) | shipped |
| Lowest common ancestor | shipped (added for HIER class H7) |
| Registry, staleness, rebuild, decline diagnostics | shipped |
| Snapshot round-trip (declaration; structure rebuilds) | shipped |
| `CREATE`/`DROP`/`REBUILD`/`SHOW HIERARCHY INDEX` | shipped |
| `subsumes()`, `hierarchy_rollup()`, `hierarchy_lca()` | shipped |
| Rewrite 2 — subtree aggregate ⇒ `HierarchyRollup` | shipped |
| Rewrite 3 — subtree enumeration ⇒ `HierarchyDescendantScan` | shipped |
| **Rewrite 1 — order test ⇒ `HierarchyOrderTest`** | **not implemented** |

The `HierarchyOrderTest` operator exists and is tested, but nothing in the planner emits
it: no detector recognizes `WHERE subsumes(d, r)` with a pinned `r` and rewrites the
cartesian product into a scan plus predicate. The consequence is measured, not guessed —
HIER classes H1 and H6 run at **0.2×** of their baseline because the function form pays a
cross product and a per-row index lookup (~500 ns/row against ~120 ns/row for a native
predicate). Until that rewrite lands, subsumption is best used through the roll-up and
descendant-scan paths, or accepted at function-call cost.

## Non-goals (v1)

- Online insert/delete maintenance of a built index.
- High-width DAGs — the index declines and defers to the traversal/2-hop path.
- Non-commutative monoids.
- Roll-up over edge properties (node measures only).
- Distributed/sharded hierarchy indexes.

## Honest scope

Order embedding, nested-set encoding, chain decomposition, and dominance-as-subsumption are
classical prior art that this builds on and does not claim. The contribution being
implemented here is the **unification** — one declarable index selected by a structural
probe, serving time, geography and ontology alike — together with **index-resident
roll-up**, where the aggregate is answered from the index rather than by an engine
aggregation the index merely filters. Genuinely low-width multi-parent DAGs appear to be
rare in practice; if the ontology corpus turns out to be mostly trees plus high-width DAGs,
the benchmark results must say so rather than selecting datasets that flatter the chain
mode.

## Follow-ups

1. **Order-test rewrite** (#349). Detect `MATCH (d:L), (r:L {pin}) WHERE subsumes(d, r)` and emit
   `LabelScan → HierarchyOrderTest` instead of a cartesian product. Highest-value
   remaining work; H1/H6 measure exactly what it is worth.
2. ~~**A hierarchy-driven plan for cross-hierarchy conjunctions** (#350).~~ **Done.** The
   axis with the smallest `descendant_count` drives through `HierarchyDescendantScan` and an
   `Expand` into the fact table; the other axes are `HierarchyOrderTest` checks. HIER H4
   went from 0.2× to 23.4× in a single before/after run; the heuristic, the cases it
   declines and the numbers are in `benchmarks/hier/README.md`.
3. **`CALL … YIELD` composition** (engine gap, not ADR-035's, tracked as #348).
   `YIELD`-bound variables are not in scope for a following `WHERE`, which blocks
   hierarchy-filtered vector search — HIER class H9 — entirely.
4. **Online maintenance** (#351). Incremental insert/delete instead of mark-stale-and-rebuild.
   Nested-set intervals are the hard case; a gap-leaving labelling would absorb some
   inserts without a full relabel.
5. **Cheaper MIN/MAX** (#352). The sparse table costs O(n log n) and dominates index size
   (7.5 MB of roll-up structures over 112 KB of order embedding on a 9,331-node ontology).
   A sqrt-decomposition or segment tree would trade a little query time for a lot of space.
6. **Real-ontology validation and a PLL baseline** (#353) — see the "Not yet covered"
   section of `benchmarks/hier/README.md`.

Tracked together in #354, with the four engine bugs the corpus surfaced (#345–#348).
